# **1. Problem-Solving (Debugging, Decision-Making Under Pressure)**   

**Q1: Describe a time you debugged a critical production issue. How did you handle it?**
During a major release at my previous company, we noticed about 30% of users were experiencing crashes when trying to access their transaction history. I immediately initiated our rollback protocol to minimize user impact while investigating. Using Sentry logs, I traced the issue to a race condition where the app was trying to access uninitialized user credentials. The root cause was an asynchronous initialization process that wasn't properly synchronized with our Redux store. I implemented a fix that added proper synchronization checks and wrote additional unit tests to cover this edge case. We then performed a staged rollout of the fix, monitoring crash rates at each 5% increment. Within 24 hours, we had reduced crashes by 95% and implemented additional monitoring to catch similar issues earlier in our CI/CD pipeline.

**Q2: How do you troubleshoot a UI freeze in a React Native app?**
When facing UI freezes, my approach begins with reproducing the issue while profiling the app using React DevTools and Flipper. I first check for JavaScript thread bottlenecks by examining component render times and looking for unnecessary re-renders. If the JavaScript thread appears clear, I then investigate the native UI thread for blocking operations. Common culprits I've encountered include synchronous storage operations, expensive image processing on the main thread, or unoptimized list rendering. For example, in one case, I discovered a frozen UI was caused by a third-party library performing synchronous file operations during component mounting. The solution involved moving this operation to a background thread and implementing proper loading states. I also use React.memo and useMemo strategically to prevent unnecessary component updates that can contribute to jank.

**Q3: A live app suddenly starts crashing on Android only. What's your process?**
My first step is to gather crash reports from Firebase Crashlytics to identify the stack trace and affected devices. I then attempt to reproduce the issue on an emulator configured with the same Android version and device specs as reported in the crash logs. If reproduction proves difficult, I'll check for recent changes that might be Android-specific, such as native module updates, Gradle dependency changes, or manifest modifications. One memorable case involved crashes only on Android 11 devices due to a scoped storage permission issue with a file handling library. The solution required updating our file access strategy while maintaining backward compatibility. I always document these investigations thoroughly and add regression tests to prevent recurrence.

**Q4: How do you handle a last-minute API change that breaks your app?**
When faced with an unexpected API change, my immediate action is to implement a feature flag that allows us to toggle between the old and new API versions. I then work on implementing graceful degradation - the app should still provide core functionality even if some features are temporarily limited. For example, in a payment app, if the transaction history API changes, I might show cached data with a refresh indicator while handling the new response format. Simultaneously, I communicate with the backend team to understand the change timeline and coordinate any necessary client-side adjustments. I've found that maintaining a well-documented API contract and implementing contract tests can help prevent these situations in the future.

**Q5: Your app's startup time increases by 3 seconds. How do you fix it?**
Investigating startup performance regression requires a methodical approach. I begin by measuring the current startup sequence using Android Studio's profiler for Android and Xcode Instruments for iOS. Typically, I'll discover the delay stems from one of three areas: excessive native module initialization, large JavaScript bundle loading, or blocking operations in the splash screen. In one optimization effort, I reduced startup time by 2.5 seconds by implementing several changes: lazy-loading non-critical native modules (like analytics SDKs) after the app becomes interactive, enabling Hermes engine for faster JavaScript execution, and restructuring our initial Redux state hydration to be non-blocking. I also introduced performance monitoring for startup time as part of our CI pipeline to catch regressions early.

**Q6: How do you decide whether to roll back or hotfix a bug?**
The decision between rolling back or hotfixing depends on several factors. I consider the severity of the bug - data corruption or security issues almost always warrant an immediate rollback. For less critical issues, I evaluate the impact radius (how many users are affected) and whether there's a workaround. A recent example was when we discovered a bug that caused incorrect balance displays for about 5% of users. Since it didn't affect actual transactions and we had a hotfix ready for QA, we chose to push the fix rather than roll back. However, when we encountered a crash affecting login for 30% of users, we immediately rolled back while working on the fix. I always document these decisions in post-mortems to refine our release strategy.

**Q7: Describe a time you had to make a tough technical decision under pressure.**
During a Black Friday sale event, our payment processing system began failing for about 15% of transactions due to unexpected load on our primary payment gateway. With revenue-critical transactions failing, I had to quickly decide between attempting to fix our current implementation or switching to our fallback provider. After analyzing the errors, I realized the issues were fundamental to our primary gateway's architecture and wouldn't be quickly resolvable. I made the call to switch all traffic to our secondary provider, despite knowing this would temporarily disable some premium features. I simultaneously worked with the team to implement a queueing system for failed transactions to retry later. This decision saved approximately $250,000 in potential lost transactions during the event, though it required significant cleanup work afterward to reconcile the two payment systems.

**Q8: How do you handle conflicting feedback from QA and Product teams?**
When receiving conflicting feedback, I first work to understand each perspective fully. I recall a situation where QA flagged a payment flow as "too complex" while Product insisted it matched their specifications exactly. I organized a joint session where QA could demonstrate the pain points they observed during testing, and Product could explain the business rationale behind the design. Through this, we identified that the core issue wasn't the flow itself but inadequate loading states that made it feel sluggish. The solution involved keeping Product's required steps while implementing QA's suggestions for better feedback during transitions. I've found that facilitating direct communication between teams, grounded in actual user data, typically reveals solutions that satisfy both quality and business requirements.

**Q9: Your app is draining battery. How do you diagnose and fix it?**
Battery drain issues require systematic investigation across several potential culprits. I start by using Android's Battery Historian and Xcode's Energy Log to identify abnormal power consumption patterns. Common issues I look for include excessive network requests in the background, unoptimized location tracking, or wake locks held too long. In one case, I discovered our app was responsible for 40% of battery drain on certain devices due to an overly aggressive sync mechanism that pinged the server every 2 minutes. The fix involved implementing adaptive sync intervals based on device charging state and network conditions, reducing battery impact by 65%. I also added battery impact monitoring to our performance metrics dashboard to catch regressions early.

**Q10: How do you prevent regression bugs in a fast-moving codebase?**
Maintaining stability in a rapidly evolving codebase requires a multi-layered testing strategy. I implement a pyramid approach with unit tests covering core business logic, integration tests for critical user journeys, and a subset of end-to-end tests for key happy paths. To make this sustainable, I focus on making tests fast and reliable - for example, mocking expensive operations and avoiding flaky UI tests. I also introduced a "commit checklist" that requires engineers to verify their changes don't break existing tests and to add new tests for any bug fixes. In one project, this approach reduced regression bugs by 60% over six months while maintaining our release velocity. We complemented this with visual regression testing for UI components to catch unintended layout changes.

**Q11: A dependency you rely on is deprecated. What's your plan?**
When facing dependency deprecation, I first assess the risk level by checking if there are security patches or critical bug fixes we might miss. I then research alternatives, considering factors like community support, maintenance activity, and API compatibility. For a recent case where our main networking library was deprecated, I created a migration plan that involved: first wrapping the existing library in an abstraction layer, then gradually implementing the new library behind this interface, and finally removing the old dependency once all features were verified. This approach allowed us to migrate over two sprints without disrupting feature development. I also documented lessons learned to improve our dependency evaluation process for future selections.

**Q12: How do you debug a memory leak in React Native?**
Debugging memory leaks in React Native requires investigating both JavaScript and native memory usage. I start by using Chrome DevTools to take heap snapshots and identify retained objects in the JavaScript context. Common issues here include uncleaned event listeners or large caches that aren't properly released. If JavaScript memory appears normal, I then examine native memory using Xcode's Instruments or Android Profiler. One tricky leak I resolved was caused by a native module maintaining strong references to JavaScript callbacks. The solution involved modifying the native code to use weak references and properly cleaning up on unmount. I've found that establishing memory usage baselines during development helps identify leaks early before they reach production.

**Q13: Your team disagrees on two technical approaches. How do you decide?**
When faced with technical disagreements, I facilitate a structured decision-making process. First, I ensure both options are clearly articulated with their pros and cons documented - considering factors like performance, maintainability, and alignment with our long-term architecture. I then suggest implementing quick spikes or prototypes if the differences are substantial. For example, when deciding between two state management approaches, we allocated two days for parallel prototypes that we then evaluated against our core criteria. This empirical approach often reveals unexpected tradeoffs and builds team consensus. If disagreements persist, I'll seek input from a neutral senior engineer or establish metrics to objectively evaluate the options in production.

**Q14: How do you handle a security vulnerability reported in a library you use?**
My response to security vulnerabilities follows a prioritized approach. First, I verify the vulnerability's severity using the CVSS score and assess whether it affects our actual implementation (sometimes features aren't used). For critical vulnerabilities, I immediately assemble a task force to implement a fix - this might involve updating the library, applying a temporary patch, or disabling affected features. In one instance, we had to quickly replace a cryptographic library that was found to have vulnerabilities, which required careful coordination to maintain data compatibility. I always document these incidents thoroughly and use them to refine our dependency management strategy, such as implementing automated vulnerability scanning in our CI pipeline.

**Q15: Describe a time you had to sacrifice perfection for speed.**
During a regulatory deadline for implementing Strong Customer Authentication (SCA), we faced a choice between shipping a fully polished solution or meeting the compliance deadline with a minimal implementation. I chose to prioritize compliance by shipping a basic but fully functional authentication flow that met all legal requirements, while documenting known UX shortcomings in our backlog. This decision allowed us to avoid potential fines while giving us time to iteratively improve the user experience post-launch. The initial version had longer authentication times, but we optimized this in subsequent releases based on user feedback. This experience taught me the importance of clear communication with stakeholders about tradeoffs between speed and quality.

**Q16: How do you ensure your app works offline?**
Implementing robust offline support requires designing for several scenarios. I architect the app to maintain a local cache of critical data using SQLite or Realm, with a synchronization system that queues changes when offline. For example, in a banking app, I implemented a dual-write strategy where transactions are first recorded locally then synchronized when connectivity is restored, with conflict resolution based on transaction timestamps. The UI is designed to clearly indicate offline status and show which data might be stale. I also implement periodic background syncs when connectivity is available to keep data as fresh as possible. Testing offline scenarios thoroughly is crucial - I create test cases that simulate various network conditions and recovery scenarios.

**Q17: Your app's size exceeds Google Play's limit. How do you reduce it?**
When facing size limits, I conduct a thorough analysis using Android Studio's APK Analyzer to identify optimization opportunities. Common strategies include: removing unused resources and alternate density assets, enabling ProGuard/R8 for code shrinking, and splitting features into dynamic feature modules. In one project, I reduced our APK size by 40% through several measures: converting large PNG assets to WebP format, removing x86 native libraries (while keeping arm64), and lazy-loading non-essential features like customer support chat. I also established size monitoring in our CI pipeline to prevent regression. For ongoing management, I created a "size budget" for new features to maintain awareness of the impact of new dependencies.

**Q18: How do you handle a failed deployment?**
My approach to failed deployments prioritizes quick recovery followed by thorough analysis. I first initiate our rollback procedure to restore the previous stable version, then communicate clearly with stakeholders about the situation and expected resolution timeline. Once stable, I lead a blameless post-mortem to identify root causes - common issues I've encountered include environment mismatches, insufficient testing of migration scripts, or unexpected interactions with live data. For example, one deployment failed because our staging database was significantly smaller than production, causing timeout issues we hadn't anticipated. From this, we implemented production-like data sizing in our staging environment and added more comprehensive rollout monitoring.

**Q19: How do you stay calm during a high-severity outage?**
During critical outages, I focus on systematic problem-solving while maintaining clear communication. I start by quickly assembling the right team and establishing clear roles - someone to investigate, someone to communicate updates, and someone to coordinate fixes. I recall a payment processing outage where I kept the team focused by breaking down the problem into testable hypotheses ("Is it the API? The network? Our client code?") and methodically eliminating possibilities. Regular, concise updates to stakeholders (even if just to say "we're still investigating") help maintain trust. After resolving the immediate issue, I make time to decompress and reflect on what went well in the response and what could be improved.

**Q20: How do you validate a fix for a complex bug?**
Validating complex fixes requires more than just verifying the specific issue is resolved. I first ensure I can reliably reproduce the original bug, then test the fix in an environment that closely matches production. Beyond the immediate fix, I look for related edge cases that might be affected - for example, fixing a race condition might introduce new timing dependencies elsewhere. I also consider adding regression tests that specifically target the failure scenario. In one particularly tricky case involving memory corruption, I created a specialized test harness that could simulate thousands of iterations of the problematic operation to verify the fix's stability. Documenting the validation process thoroughly helps build confidence in the fix and aids future debugging.

# **2. Leadership (Mentorship, Driving Best Practices)**  

**Q1: How do you onboard a new engineer to your React Native codebase?**
A structured onboarding process is crucial for helping new engineers become productive quickly while understanding our codebase architecture. I begin by pairing them with an onboarding buddy who guides them through their first 2-4 weeks. We start with setting up their development environment using a documented checklist that covers everything from Node version to Xcode configurations. Their first task is always a small, well-defined bug fix or minor feature that touches multiple parts of our stack - this gives them exposure to our state management, navigation, and testing frameworks. I provide them with an architectural overview document that explains our folder structure, key design decisions, and patterns we follow. We also conduct "code tours" where senior engineers walk through important parts of the codebase. What I've found most effective is scheduling regular check-ins during their first month to address questions and gradually increase their responsibility as they demonstrate understanding.

**Q2: Describe a time you improved your team's productivity.**
At my previous company, I noticed our development velocity was slowing due to lengthy PR review cycles averaging 5-7 days. After analyzing the bottlenecks, I implemented several changes that improved our workflow significantly. First, I introduced a PR size guideline - no PR should exceed 300 lines of code (excluding tests) unless exceptional circumstances warranted it. This forced us to break down features into smaller, more reviewable chunks. Second, I created a standardized PR review checklist that included items like "Are all new states covered by tests?" and "Is the code consistent with our style guide?" This made reviews more efficient and consistent. Third, I scheduled dedicated "review hours" where team members focused solely on reviewing PRs. Within three months, our average PR review time dropped to under 24 hours, and more importantly, the quality of reviews improved as reviewers could focus on smaller, more manageable changes.

**Q3: How do you handle a disengaged team member?**
When I notice a team member becoming disengaged, I approach the situation with empathy and curiosity rather than immediate criticism. I schedule a private 1:1 conversation where I express my observations neutrally ("I've noticed you've seemed less involved in our recent planning sessions") and ask open-ended questions to understand their perspective. Often, the root cause isn't immediately apparent - in one case, a senior engineer was disengaging because they felt their expertise wasn't being utilized effectively. By reassigning them to lead a challenging performance optimization project that played to their strengths, their engagement and productivity improved dramatically. For cases where the disengagement stems from burnout, I work with the individual to adjust their workload and encourage time off. If the issue persists despite these interventions, I escalate to HR with documentation of the concerns and attempted solutions.

**Q4: How do you advocate for tech debt reduction?**
Advocating for tech debt reduction requires framing it in terms of business impact rather than purely technical benefits. I maintain a prioritized tech debt backlog where each item includes both the technical rationale and the business consequences of not addressing it. For example, when advocating for modernizing our navigation stack, I demonstrated how the current implementation was causing 15% of our support tickets and slowing feature development by an estimated 20%. I've found success with allocating a fixed percentage (typically 10-20%) of each sprint to debt reduction, showing how this investment pays off in faster delivery over time. I also tie debt reduction to specific business goals - one compelling argument was showing how reducing our bundle size would decrease user abandonment during install, directly impacting our conversion metrics. Regular "tech debt showcases" where we demonstrate improvements to stakeholders help maintain visibility and support for these efforts.

**Q5: How do you mentor someone struggling with React Native performance?**
Mentoring engineers on performance optimization requires both technical guidance and hands-on learning opportunities. When working with an engineer struggling with performance issues, I start by pairing with them to profile the application using tools like React DevTools, Flipper, and Xcode Instruments. We examine real performance bottlenecks together, discussing why certain patterns cause issues (like unnecessary re-renders from inline functions). I then assign them small, focused optimization tasks - perhaps improving the rendering of a single list item - before moving to more complex scenarios. I share curated resources like React Native's performance documentation and case studies from our own codebase. One effective technique I've used is "performance katas" - we take a known performance problem in our app and both work on solutions independently, then compare approaches. This builds their skills while often yielding valuable optimizations for our product.

**Q6: How do you foster collaboration between mobile and backend teams?**
Breaking down silos between mobile and backend teams requires intentional structural and cultural changes. I implement several practices to improve collaboration: First, we conduct joint planning sessions where API contracts are designed collaboratively using tools like Swagger or GraphQL schema definitions. This ensures both sides understand requirements and constraints upfront. Second, I advocate for embedded pairing - having a mobile engineer sit with the backend team during critical API development and vice versa. We've even temporarily swapped team members for short periods to build empathy. Third, we maintain shared Slack channels for real-time communication about API issues. One particularly effective practice was creating a "mobile concerns" label in our backend ticket system that guarantees mobile team review before deployment. These efforts reduced our API-related bugs by 40% and significantly improved our feature development velocity.

**Q7: Describe a time you had to say no to a stakeholder. How did you handle it?**
A product manager once requested we implement a complex financial visualization feature within a two-week timeline that would have required cutting corners on code quality and testing. Rather than outright refusing, I employed a diplomatic approach that preserved the relationship while protecting the team. I first acknowledged the importance of the feature to the business goals, then walked through a detailed breakdown of why the timeline was unrealistic, showing estimates for design, implementation, and testing phases. I proposed an alternative: we could deliver a minimal viable version in two weeks that met the core business need (showing key metrics) while deferring advanced interactions to a later release. I supported this with data showing how previous rushed features had resulted in higher maintenance costs. The stakeholder appreciated this solution-oriented approach, and we ultimately delivered a phased implementation that satisfied both quality standards and business needs. This experience reinforced that "no" is often about finding better alternatives rather than outright refusal.

**Q8: How do you ensure your team follows best practices?**
Establishing and maintaining best practices requires a combination of documentation, tooling, and cultural reinforcement. I start by codifying our standards in a living "Engineering Playbook" that covers everything from code style to performance guidelines. However, documentation alone isn't enough - we automate enforcement where possible using ESLint rules, pre-commit hooks, and CI checks. For practices that can't be automated (like architectural decisions), I implement lightweight review processes - for example, requiring a senior engineer's approval for new third-party dependencies. Regular "code health" sessions where we review parts of our codebase together help reinforce standards through peer learning. I've found that leading by example is crucial - when engineers see me writing thorough tests and following our practices consistently, they're more likely to adopt them. We also celebrate "best practice champions" who consistently produce high-quality work and help others improve.

**Q9: How do you handle a disagreement with another tech lead?**
When disagreements arise with fellow tech leads, I approach them as collaborative problem-solving opportunities rather than conflicts. Recently, I disagreed with a backend tech lead about whether to implement real-time updates using WebSockets or polling. Instead of debating abstractly, I proposed we each document our positions with pros/cons and then discuss them in a structured session. We evaluated factors like implementation complexity, scalability, and battery impact on mobile devices. When we still couldn't agree, we decided to prototype both approaches for a non-critical feature and measure their performance. This data-driven approach revealed that while WebSockets were more efficient, they introduced significant complexity that wasn't justified for our use case. We ultimately implemented a hybrid solution that used polling for most cases with WebSockets for specific high-priority updates. The key was maintaining respect for each other's expertise while letting empirical evidence guide our decision.

**Q10: How do you keep your team motivated during crunch time?**
During intense periods, I focus on balancing short-term delivery needs with long-term team health. Transparency is crucial - I explain why the crunch period exists and how it fits into broader company goals. To maintain morale, I break down the work into small, achievable milestones with visible progress tracking. I'm careful to model sustainable behavior myself - working extra hours when needed but also taking breaks and encouraging others to do the same. Small gestures like providing meals during late nights or organizing brief team decompression sessions help relieve stress. After one particularly demanding release, I implemented a "recovery period" where team members could take extra time off or work on low-stress technical debt items. Most importantly, I ensure crunch periods are the exception rather than the norm, and I advocate forcefully for more sustainable timelines whenever possible. This approach has helped my teams deliver under pressure while maintaining high engagement and low turnover.

**Q11: Describe a time you improved code quality in your team.**
When I joined a new team, I noticed their React Native codebase had inconsistent testing practices leading to frequent regression bugs. To address this systematically, I first conducted a code quality audit to identify key pain points - we had only 40% test coverage for critical paths and no established patterns for testing Redux sagas. I started small by introducing "testing dojos" - weekly sessions where we'd collaboratively write tests for problematic areas of the code. We gradually implemented stricter requirements, beginning with "all new code must have tests" before tackling legacy code. I created test templates and helper functions to make writing tests easier, and integrated coverage metrics into our CI pipeline. To sustain the effort, I tied code quality improvements to business outcomes - showing how better test coverage reduced our production bug rate by 35% over six months. The cultural shift was as important as the technical changes - by celebrating testing improvements in sprint retrospectives and recognizing engineers who wrote particularly thorough tests, we made quality a shared value rather than an imposed requirement.

**Q12: How do you delegate tasks effectively?**
Effective delegation begins with understanding each team member's strengths, growth areas, and career aspirations. When assigning work, I consider not just who can complete a task fastest, but who would benefit most from the learning opportunity. For complex tasks, I use a gradual delegation approach - starting with clear instructions before moving to more autonomous work as the engineer demonstrates capability. I'm careful to provide context about how each task fits into the larger project goals, which increases engagement and helps engineers make better implementation decisions. Regular check-ins (without micromanaging) ensure they have the support needed while maintaining ownership. One technique I've found valuable is the "delegation ladder" - being explicit about whether I'm making a decision, seeking input, or delegating completely. This clarity prevents misunderstandings. I also document delegation decisions and outcomes to ensure I'm distributing opportunities fairly and identifying areas where team members need additional support or training.

**Q13: How do you handle an underperforming engineer?**
Addressing underperformance requires a compassionate yet structured approach focused on improvement. In one case, an engineer was struggling because personal issues were affecting their focus - we worked with HR to arrange a temporary reduced workload. For example, for an engineer struggling with React Native performance issues, we set specific targets around reducing re-renders in their components and scheduled weekly pairing sessions. Documentation is crucial - I keep detailed notes of expectations, feedback given, and progress made. If performance doesn't improve despite these efforts, I work with HR on next steps, always ensuring the process is fair and transparent. Throughout, I balance honesty about performance gaps with genuine belief in the individual's potential to improve.

**Q15: How do you align your team with company goals?**
Team alignment with company objectives requires continuous, multi-level communication. I start by breaking down high-level company goals into specific engineering implications - for example, if the company is focusing on user retention, I'll work with product to identify the technical factors that most impact retention in our app. I then facilitate sessions where the team translates these into concrete technical initiatives, like improving app startup time or reducing crash rates.
